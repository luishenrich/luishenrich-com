The most-asked question I get is some variation of *what does StudyPDF actually run on?* This post is the long answer. It&rsquo;s not advice — &ldquo;use what works for you&rdquo; is real — but it is a snapshot of what works for one solo founder serving 85,000 users on a budget that wouldn&rsquo;t cover an FTE.

## The constraints

Three things shape every choice on this list:

1. **One person on call.** I can&rsquo;t afford anything that pages me at 3am unless I&rsquo;ve already lost.
2. **Spiky load.** Exam season pushes traffic 8–10x baseline for ten days, then it&rsquo;s quiet again.
3. **PDF-heavy.** The product is documents in, documents out. I/O dominates compute.

If your constraints look different — VC-funded, team of ten, evergreen traffic — substitute accordingly.

## Hosting and runtime

Next.js on Vercel for the web app. I evaluated rolling my own — it&rsquo;s tempting, especially after the bill arrives — but every time I price out the engineering hours against the platform cost, the platform wins. The hidden line item is incidents I never have.

For background work I use a small worker fleet on Fly.io. PDF parsing is CPU-heavy and bursts, which is a bad fit for serverless function timeouts. Fly machines that scale to zero between waves of jobs have been the right shape.

```ts
// Worker dispatch — naive but it works
async function dispatch(job: Job) {
  await queue.add(job.id, job, {
    attempts: 3,
    backoff: { type: "exponential", delay: 2000 },
  });
}
```

## Database

Postgres on Neon. I came in skeptical of serverless Postgres for a real workload and have been quietly converted. Branching for migrations is the unsexy feature that has saved me the most time — I can spin a branch off prod, run the migration, point a preview deploy at it, and only merge if the numbers look right.

Read replicas are configured but underused. Most reads still hit primary because the query patterns are simple enough that it hasn&rsquo;t bitten me. I&rsquo;ll regret this eventually.

## Storage

S3 for raw PDFs. Cloudflare R2 for processed artifacts and exports — egress pricing alone justifies the move for the output side. I keep both because R2&rsquo;s consistency story for write-heavy workloads still makes me nervous for source-of-truth data.

## Auth

Clerk. Boring, expensive at scale, and worth every cent until I can afford to think about auth full-time, which is approximately never.

## What I&rsquo;d change

Two things, if I were starting today:

- **Skip the worker queue abstraction.** I built a small custom layer over BullMQ early on. It earned its keep for about six months and has been a tax ever since. The tells were obvious in retrospect: I was reaching past my abstraction more than I was using it.
- **Pick a vector store earlier.** I bolted retrieval onto Postgres with pgvector when usage was small, and migrating off it under load wasn&rsquo;t fun. If you know you&rsquo;re going to need a serious vector workload, just start with a serious vector workload.

## What surprised me

How much of this is unremarkable. There&rsquo;s a fantasy, when you&rsquo;re reading other founders&rsquo; stack posts, that they&rsquo;ve found some clever combination you haven&rsquo;t. Mostly they haven&rsquo;t. The leverage is in the boring parts done with care.
